# ADR 0003：分离 Task 业务状态与 AgentRun 执行状态

- 状态：Accepted
- 日期：2026-08-03

## 背景

一个学习任务可能经历多次笔记验收、回答验收和失败重试。任务对用户表达的是长期学习进度；一次 Agent 执行则可能排队、运行、取消、失败或超时。若两者共用状态字段，一次基础设施故障就可能被错误解释成“笔记验收不通过”，重试也会覆盖历史尝试。

## 决策

`Task.state` 只描述业务进度，例如 `IN_PROGRESS`、`NEEDS_REVISION`、`NEEDS_EVIDENCE` 和 `PASSED`。`AgentRun.status` 只描述一次执行尝试，例如 `QUEUED`、`RUNNING`、`FAILED` 和 `TIMED_OUT`。

运行开始前保存 `taskStateBeforeRun`。运行失败、取消或超时后，应用使用 Task 的版本字段做乐观并发校验，只允许恢复到这次运行实际保存的稳定状态，不能覆盖运行期间已经发生的更新。重试创建新的 `AgentRun`，通过 `retryOfRunId` 关联旧记录，不覆盖失败记录。

跨进程字段由 `packages/contracts` 中的 TypeScript 常量、Zod Schema 和 DTO 约束；PostgreSQL 的 Prisma 枚举保存相同业务值。展示颜色、按钮文案和页面筛选不进入共享契约，由 Web 根据状态自行映射。

## 结果

- Worker 故障不会直接把 Task 标成验收失败，技术失败和业务结论可以分别展示。
- 一项任务可以保留多次运行尝试，支持审计、重试和后续可靠性指标。
- 状态更新需要同时校验合法迁移和版本，写入逻辑比单字段状态更明确但也更严格。
- TypeScript/Zod 与 Prisma Schema 中存在枚举值的显式重复；目前用生成后的 Prisma 枚举与共享常量做一致性测试，不引入额外代码生成器增加阶段 1 的复杂度。

## 放弃的方案

- 单一状态机：状态数量会形成业务进度与执行状态的笛卡尔积，失败恢复含义模糊。
- 失败时覆盖原运行：无法解释重试链，也会丢失错误、耗时和成本证据。
- 把 UI 展示字段放进共享 DTO：会让 API/Worker 契约反向依赖某个页面设计。
