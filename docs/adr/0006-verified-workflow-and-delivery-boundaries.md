# ADR 0006：当前验收链路、前端恢复与交付边界

- 状态：Accepted，整理既有实现，不新增架构。
- 日期：2026-11-09（R18）。
- 关联：ADR 0003、0005；R13/C2、R06、R09 至 R17、CD01 至 CD03。

## 背景

早期 ADR 描述了计划生成，但当时尚无完整 GitHub 验收和部署。现在需要对齐演示、README 与真实实现，避免把后续规划误当成当前能力，或把测试替身误当成真实模型证据。

## 决策与代价

| 选择 | 解决的问题 | 代价与边界 |
| --- | --- | --- |
| PostgreSQL 保存业务意图与 Outbox，BullMQ 负责调度 | Redis 暂不可用时，已提交的业务意图仍可补投；模型等待不占用请求连接 | 需要分别恢复投递失败和消费失败；相同 jobId 不能代替业务幂等 |
| 固定 Commit SHA、原绑定及 Task 版本 | 排队期间仓库继续变化时，报告仍能解释验收的是哪份内容 | 绑定失效、版本过期或旧提交不可读必须退出或显式恢复，不能悄悄改读最新内容 |
| 执行账本与业务 Finalizer 分工 | 已保存完整执行结果但业务事务失败时，可复用结果完成落库 | 模型响应与账本保存之间仍有不确定窗口；不承诺所有故障下模型只调用一次 |
| 分离 Run、报告结论和 Task | 一次执行成功可以得出“不通过”；网络失败不等于知识错误 | 前端要清楚展示多个状态，Task 通过前须汇总全部必需标准 |
| 计划生成 SSE 快照 + HTTP 恢复，验收查询采用轮询 | 用户刷新或短暂断网后回到数据库中的可信状态 | 维护订阅生命周期、批次和版本；没有完整事件重放，SSE 服务端也会周期查询数据库 |
| CI 产物验证后手动发布，镜像摘要固定 | 发布可追溯到成功 CI 的具体尝试，VPS 不重新构建 | 镜像回退不撤销迁移，旧版本必须兼容新数据与队列事件；单实例有维护窗口 |

简单的“HTTP 内直接调用模型”减少进程和队列配置，但请求断开后很难判断执行到了哪里；本项目已有长时生成、GitHub 异步事件和恢复需求，因此承担这些复杂度。当前不增加多区域部署、另一套状态持久化或更复杂的发布编排。

## 真实调用边界

Webhook 保存 Delivery 与需要的 Outbox 后返回 202；Dispatcher 投递，Worker 取证后保存 Submission/Evidence、创建笔记 AgentRun 与下一条 Outbox。笔记执行生成报告和追问；回答提交创建独立回答 Run。两个 Finalizer 都复核归属、原始材料及版本，再原子保存相关报告、Run 终态与 Task 汇总结果。

追问等待期间不保持一个 Worker Job 运行。浏览器页面负责恢复展示与提交命令，不负责决定验收是否通过；重复发送同一回答命令保留 requestId，但服务端仍先检查用户归属。

## 验证入口

- [完整合成闭环](../../tests/e2e/learning-flow.e2e.ts)：真实请求、持久化与队列，预设登录/绑定、模拟 GitHub 和模型；核对回答确实属于本次笔记 Run。
- [计划生成恢复](../../apps/web/app/lib/plan-run-recovery-driver.ts)：SSE、HTTP 与订阅清理的执行层；状态决策由相邻 reducer 完成。
- [手动发布工作流](../../.github/workflows/release.yml)与[发布演练](../../deploy/cd03-release.md)：成功 CI 选择、产物校验、串行发布及兼容回退。
- 真实模型和生产证据见 [R18 事实清单](../demo/r18-demo.md)，不从合成测试推断准确率、用户规模或吞吐。

ADR 0005 的早期阶段记录保留为历史；其“后续接入 SSE、GitHub 和生产”的描述不再代表当前状态。对计划生成与笔记/回答验收的账本、预算能力分别按真实实现解释，不将验收账本泛化为所有模型调用都有完整费用记录。
