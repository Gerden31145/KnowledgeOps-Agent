先给一句话版本：

  新的方案不是“让 API 异步 await 模型”，而是把计划生成变成一项可持久化、可查询、可重试的后台任务。API 只负责可靠登记任务并返回“取件号” generationRunId，
  Worker 在请求结束后继续生成，前端拿取件号查询结果。

  ## 一、三种“异步”不要混淆

  我们之前容易把三件事都叫异步：

    1. Node.js 异步 I/O
     await model.invoke() 不会阻塞整个事件循环，但 HTTP 连接仍然一直开着，占用连接、内存和并发额度。

    2. 流式 HTTP / SSE
     模型生成一个 Token，浏览器展示一个 Token。体验更实时，但仍然绑定连接；刷新、断网、API 重启后，不天然具备业务恢复能力。

    3. 持久化后台任务
     API 先把“我要生成计划”写进 PostgreSQL，然后立即结束请求。之后即使浏览器关闭，Dispatcher 和 Worker 仍能继续执行。

  新方案选择的是第三种。计划不是聊天文本，而是一张必须整体通过 Schema、数量、日期和 DAG 校验的结构化图，因此当前不展示不可信的半成品 Token。

  ## 二、正常数据流

  flowchart LR
      Web[Nuxt 前端] -->|创建目标| API[NestJS API]
      API -->|保存| PG[(PostgreSQL)]

      Web -->|发起生成| API
      API -->|事务 A: Run + Outbox| PG
      API -->|202 + generationRunId| Web

      Dispatcher[Outbox Dispatcher] -->|读取未分发事件| PG
      Dispatcher -->|稳定 Job ID| Queue[BullMQ / Redis]
      Queue --> Worker[Worker]

      Worker -->|读取目标与运行快照| PG
      Worker --> Port[计划生成端口]
      Port --> LC[LangChain 适配器]
      LC --> Model[模型供应商]

      Worker -->|校验完整结果| Worker
      Worker -->|事务 B: 完整计划图 + SUCCEEDED| PG

      Web -->|轮询 generationRunId| API
      API --> PG

  ### 0. 先保存 LearningGoal

  用户填写：

  - 学习目标；
  - 当前基础；
  - 截止日期；
  - 每周投入时间；
  - 服务端模型目录中的模型 ID。

  API 先独立保存 LearningGoal。因此即使后面生成失败，用户输入也不会丢失。

  模型 API Key 只在服务端环境变量中。数据库只保存稳定模型 ID 和必要的历史快照，不保存密钥。

  ### 1. 用户发起计划生成

  前端针对已经存在的 LearningGoal 发起生成命令。

  API 先完成：

  - 用户权限检查；
  - LearningGoal 是否属于当前用户；
  - 模型 ID 是否属于服务端白名单；
  - 当前目标是否已经有一个 QUEUED/RUNNING 的生成运行。

  这里不会调用模型。

  ### 2. PostgreSQL 事务 A：登记生成意图

  API 在同一个短事务中写入两条记录：

  PlanGenerationRun
  - id
  - goalId
  - status = QUEUED
  - model/provider/prompt/schema 快照
  - deadlineAt
  - version
  - retryOfRunId

  OutboxEvent
  - type = PLAN_GENERATION_REQUESTED
  - aggregateId = generationRunId
  - dispatchedAt = null

  这两个对象必须“同时成功或同时失败”。

  如果只创建 PlanGenerationRun，然后进程在入队前崩溃，运行会永远卡在 QUEUED。如果先入队再写数据库，Worker 又可能读到一项不存在的运行。

  Outbox 的作用就是解决 PostgreSQL 和 Redis 之间无法共享同一个事务的问题。

  可以把这一步概括为：

  > 事务 A 保证“运行记录”和“需要执行这次运行的意图”原子一致。

  注意：数据库事务不会覆盖模型调用过程。我们不会开着一个 PostgreSQL 事务等待几十秒模型响应，否则会长期占用连接和锁。

  ### 3. API 返回 202 Accepted

  事务提交后，API 立即返回类似：

  {
    "generationRunId": "run-id",
    "status": "QUEUED"
  }

  202 的含义是：

  > 服务器已经可靠接受任务，但任务还没有完成。

  它不表示 Plan 已经生成，也不返回伪造的 Plan。

  此时 API 请求生命周期已经结束。用户刷新、离开页面甚至关闭浏览器，都不会取消已经提交的后台任务。

  ### 4. Dispatcher 将 Outbox 投递到 BullMQ

  Dispatcher 周期性扫描 PostgreSQL 中尚未分发的 Outbox：

  OutboxEvent
      ↓
  Queue.add(
    jobName,
    { generationRunId },
    { jobId: "plan-generation-{runId}" }
  )
      ↓
  标记 Outbox 已分发

  队列消息原则上只携带 generationRunId 等标识，Worker 再从 PostgreSQL读取真实数据。这样可以避免队列中保存密钥、完整 Prompt 或容易过期的业务快照。

  稳定 Job ID 是第一层去重：

  plan-generation-{runId}

  如果 Dispatcher 入队成功后、标记 Outbox 前崩溃，它稍后会再次尝试投递相同 Job ID。

  不过，稳定 Job ID 不是永久幂等保证：Job 被清理后仍可能重新加入，最终必须由 PostgreSQL 的状态、版本和唯一约束兜底。

  ### 5. Worker 领取任务

  Worker 从 BullMQ 取得 Job 后，根据 generationRunId 查询 PostgreSQL。

  第一次执行时，会尝试条件更新：

  QUEUED → RUNNING

  更新条件至少包含：

  - 当前运行 ID 正确；
  - 当前状态允许执行；
  - 当前版本仍然匹配；
  - 尚未超过 deadlineAt。

  如果条件更新影响 0 行，说明可能是：

  - 另一个执行者已经处理；
  - 运行已经成功；
  - 运行已经失败或超时；
  - 版本已经变化。

  Worker 不能继续盲目写数据，而应根据最新状态跳过或处理队列重试。

  ### 6. Worker 调用 LangChain 适配器

  依赖方向是：

  Worker 用例
      → 项目定义的 PlanGeneratorPort
          → LangChainPlanGeneratorAdapter
              → 模型供应商

  Worker 和业务服务只认识项目自己的输入输出，不认识 LangChain 的消息类型。

  LangChain 负责：

  - 统一模型调用接口；
  - 对接供应商 SDK；
  - 请求结构化输出；
  - 收集 Token、耗时和模型调用信息；
  - 必要的受控技术重试。

  LangChain 不负责：

  - 修改 PlanGenerationRun 状态；
  - 写 Prisma；
  - 创建 Plan；
  - 判断任务状态；
  - 控制数据库事务；
  - 决定业务重试。

  因此 PostgreSQL 仍然是唯一真相源，LangChain 只是适配器。

  ### 7. 完整校验模型输出

  模型返回的数据不能直接写入数据库。Worker 必须依次校验：

    1. Zod 结构是否正确；
    2. 阶段数量是否为 1～3；
    3. 总任务数是否为 3～8；
    4. 日期和预计时长是否合法；
    5. 临时任务 ID 是否唯一；
    6. 所有依赖引用是否存在；
    7. 任务不能依赖自己；
    8. 整张依赖图是否无环；
    9. 验收标准和 Markdown 路径等业务字段是否合法。

  在全部校验完成前，不创建任何 Plan、Stage 或 Task。即使模型已经输出了 90%，它仍然不是合法业务结果。

  ### 8. PostgreSQL 事务 B：原子落下完整计划

  校验通过后，Worker 开启第二个短事务：

  再次确认 Run 仍为 RUNNING 且版本匹配
      ↓
  创建 Plan(DRAFT)
      ↓
  创建全部 Stage
      ↓
  创建全部 Task
      ↓
  创建全部 Criterion
      ↓
  创建全部 TaskDependency
      ↓
  PlanGenerationRun → SUCCEEDED

  只要中间任何一步失败，整个事务回滚：

  Plan        不存在
  Stage       不存在
  Task        不存在
  Criterion   不存在
  Dependency  不存在
  Run         仍不会成为 SUCCEEDED

  这就是第二个核心原子性：

  > 事务 B 保证“完整计划图”和“生成成功状态”同时成立。

  如果超时清理器先把运行改成 TIMED_OUT，Worker 的条件更新会影响 0 行，整个 Plan 写入事务必须回滚。迟到的模型结果不能复活终态运行。

  生成成功后，Plan 仍是 DRAFT。只有用户确认计划，后续确认事务才会：

  - 把 Plan 改为 ACTIVE；
  - 把没有前置依赖的首批 Task 解锁为 READY；
  - 其他任务保持 BLOCKED。

  ## 三、前端如何得到结果

  前端收到 generationRunId 后，用 TanStack Query 查询服务端状态：

  QUEUED  → 继续轮询
  RUNNING → 继续轮询
  SUCCEEDED → 停止轮询，读取完整 Plan
  FAILED    → 停止轮询，显示错误和重试入口
  TIMED_OUT → 停止轮询，显示超时和重试入口

  轮询需要有退避，例如逐渐拉长间隔，并且在以下情况停止：

  - 已进入终态；
  - 页面卸载；
  - 查询被禁用；
  - 用户切换目标。

  刷新后重新从 PostgreSQL 查询当前或最近的生成运行，而不是依赖 Pinia 中的临时状态。Pinia 可以保存界面交互状态，但不复制一套 PlanGenerationRun 真相。

  阶段 5 可以把状态通知升级为 SSE，但 SSE 只改变“前端如何更快知道状态变化”，不会取代 PostgreSQL、Outbox、BullMQ 或 Worker。

  这里必须诚实说明：

  > BullMQ 的“至少一次执行”能保证最终尝试处理，但不能保证外部模型恰好只调用一次。

  如果 Worker 已经拿到模型结果，却在保存前崩溃，重试可能再次调用模型。我们能保证的是：

  - 不会创建两份有效 Plan；
  - 不会把终态重新改回运行中；
  - 会记录尝试和成本；
  - 会限制 SDK、LangChain、BullMQ 的总重试预算。

  ## 五、两种“重试”也要区分

  技术重试：

  同一个 PlanGenerationRun
  同一个 BullMQ Job
  处理临时网络错误

  用户重试：

  旧 Run = FAILED/TIMED_OUT，保持不变
  新建 Run = QUEUED
  newRun.retryOfRunId = oldRun.id

  终态运行永远不复活。这样可以保留每一次失败历史、模型快照、耗时和错误原因。

  状态机是：

  QUEUED → RUNNING → SUCCEEDED
                   → FAILED
                   → TIMED_OUT

  QUEUED ─────────→ TIMED_OUT

  ## 六、为什么不用原来的 AgentRun

  现有 AgentRun 必须关联 Task，还保存了 taskStateBeforeRun，它表达的是：

  > 某个已经存在的学习任务正在进行笔记验收或回答验收。

  但生成计划时，Task 根本还不存在。因此我们单独使用：

  - PlanGenerationRun：生成 Plan 的一次尝试；
  - AgentRun：对某个 Task 进行验收的一次尝试。

  这能避免为了复用一张表，把 taskId、goalId、taskStateBeforeRun 都改成大量可空字段。当前基线模型可以从 /D:/project/agent/prisma/schema.prisma:56 看到；08-07
  才会正式加入新的运行和 Outbox 模型。
