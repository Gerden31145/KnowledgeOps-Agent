2026-09-05 用户已授权减负重排。对未完成工作执行本技能的新流程：按学习单元交付、陌生技术先入门、每周约两次小手写、九月剩余两项核心手写、每次短复述和每周一次问答。旧日历、每日微观题和每阶段强制核心手写不再作为后续前置条件；已完成学习、提交和历史问答不返工、不改写。

识别当前请求：

- **计划调整**：落实已经确认的范围、学习规则、预算和状态映射；更新冲突文档与技能入口。不得把计划获批当成新阶段产品实现已授权。
- **继续开发**：读取当前活动阶段与下一单元，沿已授权状态继续；普通“继续”不能代替首次授权或手写前理解确认。
- **代码提问**：结合真实调用链解释当前问题；不因回答问题自动推进状态，也不把已确认背景全部重讲。
- **手写/Review/问答**：按下表路由，只执行当前关卡，不泄露未完成手写答案。

## 状态与路由

阶段状态：`NOT_STARTED → EXPLAINING → AI_IMPLEMENTING → VERIFYING → DOCUMENTING → DONE`，外部阻塞可暂记 `BLOCKED` 并保存返回状态。只有一个阶段活动；历史阶段状态原样保存在归档中。

学习单元状态：

`NOT_STARTED → PREREQUISITE（按需）→ WORKING → WALKTHROUGH → WAITING_USER_CODE（有手写时）→ REVIEWING → RECALL → DOCUMENTING → DONE`

- 已具备基础时跳过 `PREREQUISITE`。
- 非手写单元在用户确认理解后从 `WALKTHROUGH` 进入 `RECALL`，无需制造缺口或经历 Review。
- 独立基础入门单元在 `PREREQUISITE` 完成示例、用户观察与简短导读后进入 `RECALL`；只有形成真实实践证据才可完成。
- 核心手写单元可以复用已完成主体和已有理解确认，但仍需完成本次手写业务上下文的导读与理解确认，再进入 `WAITING_USER_CODE`；不重做旧日关卡，不用旧技术入口的理解确认替代新业务的理解确认。
- 外部阻塞用 `BLOCKED`；经已授权裁剪移出本期的单元用 `DEFERRED`。两者都不是完成状态，不因到达日历日期自动改为 `DONE`。

| 当前状态或用户信号 | 下一动作 |
| --- | --- |
| 新阶段尚未授权 | 简短说明 IN、OUT、演示标准、主链路和失败路径，解释后等待明确实现授权 |
| 已授权，单元未开始 | 明确本轮一个新概念、可观察结果、预算和 2 至 3 个核心入口，按需先入门 |
| `WALKTHROUGH`，用户有疑问 | 解释真实代码；若修改则重跑相关检查，不提前交付手写 |
| 用户明确理解主体且该单元有手写 | 先完成下述手写前业务导读，确认本题上下文已理解，再交付接口、验收与提示，进入 `WAITING_USER_CODE` |
| 用户表示手写未完或询问提示 | 只澄清背景和分层提示，不补完核心答案 |
| 用户明确说写完 | 进入 `REVIEWING`，检查代码及专用验收 |
| Review 有 blocking 问题 | 给原因与提示，等待用户修正；不能由 AI 代写后宣布通过 |
| Review 通过 | 回归、说明在完整链路中的作用，再进入短复述 |
| 短复述已完成 | 记录实际耗时、证据和未解问题，进入 `DOCUMENTING` 并提交 |
| 用户回答正在进行的周问答 | 评价后给标准答案；如仍有时间再问下一道，结束即写档 |

新阶段的首次授权保留；既有阶段授权和旧单元的理解确认继续有效。不要求用户重复批准同一动作。计划调整请求完成文档与验证后可以直接创建范围明确的计划提交，不进入产品手写或面试题。

## 控制交付规模与基础入门

2026-11-04 用户授权适量合并后续小阶段。优先将同一业务目标、共享上下文的相邻小段组织为一批，统一实施与验证，再集中导读、理解确认和一次短复述；不按文件、命令或单个测试反复设关卡。可复用跨单元的准备、讲解与证据，但保留原编号及各自完成条件，顺序更新一个活动单元，不能批量宣告未验收工作完成。具体分组写入现行计划，不重开已完成学习。

每个合并批次围绕一个主要新概念和完整可观察结果，首轮必读约 2 至 3 个核心文件，允许跨学习时段完成。若理解依赖三种陌生机制或出现独立风险，按实际缺口拆分；不能只缩短文件清单却让用户承担同样多的隐含知识。合并减少重复准备与停顿，不扩大业务范围或总预算，也不省略已有授权边界、手写理解确认与关键验收。

AI 复用现有 Queue、模型端口、契约与状态规则，避免重复封装、未来扩展抽象和无业务用途的练习文件。其他文件按职责、接口、风险与测试证据说明；测试与安全质量不因少读文件而降低。

陌生技术的入口采用“最小运行 → 修改一个输入或行为 → 观察结果 → 映射到项目装配”。BullMQ 首次安排约 45 至 60 分钟，覆盖 Redis 连接、Queue、入队、Worker 消费、停止与恢复；NestJS、Prisma、SSE 只补已识别的基础缺口。时间替代原导读和细节追问，计入该单元，不能追加为课外作业。

允许完整讲解独立基础示例，但示例不得包含尚未完成核心手写的等价业务实现。最小用法尚未建立时，暂不交付依赖它的复杂业务题。

## 主体实现与导读

1. 检查工作树并只实现当前单元已确认范围，保留用户已有改动。
2. 有手写安排时只准备 `TODO(user)` 或等价缺口、接口和黑盒验收；其他单元正常完成产品实现，不为了练习留空。
3. 运行风险相称的 lint、类型检查、单元、集成或 E2E。手写缺口导致的预期失败单独说明，不能掩盖其他失败。
4. 进入 `WALKTHROUGH`：先说明用户能看到什么，再结合业务目的、数据流和架构设计给出核心入口、调用链、关键选择、一个失败路径、未实现范围和实际验证方式。架构讲解结合真实代码或配置，说明模块/进程的职责与依赖、接口边界、状态归属。每个关键设计点用一两句话解释设计原因：解决什么实际问题、为何适合当前规模、主要代价是什么，必要时简要对比一种更简单的方案；按本次问题选择重点，区分已实现设计与计划能力，不空讲分层或追加技术栈。部署单元相应解释流量入口、进程与存储的关系、发布顺序及失败恢复责任。沿计划现有主链路图补充必要边界，计入原导读预算，不新增架构考试或第二套必读文档。有手写时还须完成下述业务上下文导读，不能只说明位置与学习价值。
5. 用户确认理解前继续补上下文、回答问题；确认本次手写业务后才进入手写，非手写单元则进入短复述。代码变化时补充验证和解释，不重复展示全量 diff。

## 手写与 Review

### 动笔前：业务与上下文导读

适用于小手写与核心手写，由 AI 主动带读，不能仅发题面、术语表和验收让用户自行拼出业务。先说明真实业务问题与函数用途；沿调用链讲清调用者、触发时机、输入来源、输出消费者，以及配套代码已完成什么、用户只需决定什么。按需补齐本题模型、字段、状态与术语，不扩展成全项目通读。

用具体数据走通正常路径和关键失败/边界路径，说明事件、前后状态、预期结果及业务理由。异步题还须交代通知来源、可能的先后顺序，以及业务状态/同步状态、数据版本/本地批次的区别。解释业务要求不等于泄露答案：不提供完整核心实现、可照抄的等价伪代码或相邻参考实现。

通过简短交流，让用户用自己的话说明函数用途、数据进出与关键场景的预期行为，并确认理解后才交付手写任务；不新增考试或评分。主体入口已读懂不代表新手写上下文已读懂。仍不清楚时留在导读补缺口；编码中暴露同类缺口时也先回到业务场景，不连续用失败断言替代教学。此环节计入原准备预算、替代碎片追问，不追加课程，也不重开已通过手写。

### 编码与验收

小手写按计划每周约两次、每次 25 至 35 分钟；没有安排的单元无需额外练习。短周、核心手写周和冻结期不凑次数。

剩余核心手写只有：

- C1：阶段 2 完整 Plan 图与 `SUCCEEDED` 原子落库；
- C2：前端运行状态恢复；按 9/16 调整前移，固定练 SSE 快照恢复、Run/版本隔离、订阅清理与轮询兜底。只做一份，后续工作台复用；不补历史重放或另一份轮询题。

原阶段 3、4、6 的业务与测试由正常单元交付，不再附加独立阶段核心手写。此前已完成的阶段 1 核心手写保留。

交付只包含背景、文件和签名、输入输出、不变量、3 至 6 个小题验收或 5 至 10 个核心验收、运行命令与分层提示。不提供完整答案，不在相邻文件藏等价实现。小题获得提示后仍预计超过 45 分钟，拆除机械工作并收窄题面；核心题保持 1 至 2 小时的核心编码量，准备与 Review 另计但必须纳入单元预算。

用户明确完成后才 Review：检查业务正确性、边界、类型、可读性和可解释性，区分 blocking 与 non-blocking。blocking 由用户修正，机械格式可代为修整并说明。通过专用验收及相关回归后，补充手写在调用链中的作用与 Review 结论。

C1、C2 各自独立本地提交；小手写随所属单元提交。不得修改黑盒验收绕过失败，也不把待实现、待 Review 或被延期的工作记录为已完成。

## 短复述、细节与周问答

每次学习收尾约 5 分钟，让用户复述本次链路或更新计划中的六节点简图。判断理解是否足够的依据：用途、输入输出与调用者、最小修改的验证方式、一个关键失败场景。不是要求逐个追问四道新题，也不是要求清空所有疑问。

普通细节探索超过 15 分钟仍无进展，记录疑问、入口和触发深入的场景，每周最多深挖一个。权限、数据丢失、重复写入和终态覆盖等关键不变量必须厘清。长文档仅按需查询；不生成另一份必须全文背诵的大纲。

按计划每周一次约 20 分钟问答，优先重复薄弱点、最近手写和跨模块因果。一次一道主问题，最多两个紧密相关追问；剩余问题放下次，不延长为考试串。用户回答后评价、指出遗漏、给面试表达参考，评分可选。此问答兼作阶段复盘，不再叠加每日新题与每阶段宏观题。

结束后立即追加到 `问答.md`：实际日期、关联单元、真实回答要点、评价、易错点、参考答案与一项复习动作。短复述只在单元进度中简记，不虚构问答记录。周问答独立提交，不强制等待下一次周问答才关闭已验收的单元或阶段。

## 验证、状态与本地提交

完成单元需要行为验收、相关检查、导读与理解确认、该单元所安排手写的 Review、短复述和进度记录；基础入门则保存实际操作与观察证据。未安排的手写和正式问答不成为隐含关卡。

提交流程：

1. `git status --short` 区分本单元、既有无关改动和其他单元内容。
2. 仅按明确路径暂存当前范围，检查暂存 diff 和 `git diff --cached --check`；排除密钥、环境文件与调试产物。
3. 进度状态与成果同一提交；准备提交时写 `DONE`，仅 commit 成功后对外宣布完成并报告哈希。
4. 提交失败时保持或恢复 `DOCUMENTING`，排查并解决；不 amend、rebase、改写历史或推送远端。
5. 核心手写提交、独立周问答、计划调整与阶段收尾保持范围清楚；不要为了每日打卡补造提交。

阶段关闭前核对确认范围、关键失败路径、相关测试、所安排手写和实际学习记录。被裁剪单元明确记 `DEFERRED`，阶段只能按剩余确认范围完成；记录实际日期和偏差，随后只预告下一阶段。
