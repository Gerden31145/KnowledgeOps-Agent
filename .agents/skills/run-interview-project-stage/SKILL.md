# Run Interview Project Stage

## 读取项目上下文

按顺序读取：

1. 根目录 `AGENTS.md`；
2. `docs/KnowledgeOps-Agent-9月求职版PRD.md`；
3. `docs/KnowledgeOps-Agent-逐日开发计划.md` 的阶段看板、当前计划日及其状态；
4. 根目录 `问答.md` 中已完成的每日与阶段薄弱点；
5. 当前阶段涉及的源码、测试和 ADR。

将 PRD 视为产品范围真相源，将逐日计划的阶段看板与每日状态视为流程状态真相源。发现二者冲突时，先指出冲突，不静默扩大范围。

## 识别当前意图

同时检查阶段状态与当前计划日状态：

| 条件 | 用户信号 | 下一动作 |
| --- | --- | --- |
| 阶段 `NOT_STARTED` | 开始/继续某阶段 | 进入阶段需求确认 |
| 阶段 `REQUIREMENTS_CONFIRMING` | 用户确认需求 | 进行阶段讲解 |
| 阶段 `EXPLAINING` | 用户明确说“明白了”“可以开始”“开始写吧”等 | 授权阶段实现 |
| 阶段 `AI_IMPLEMENTING`，计划日 `NOT_STARTED` | 开始/继续今天计划 | 只执行该计划日 |
| 计划日 `DAILY_WALKTHROUGH` | 用户查看代码、询问改动或表示尚未理解 | 继续结合真实文件讲解，不进入面试问答 |
| 计划日 `DAILY_WALKTHROUGH` | 用户明确说“改动明白了”“可以提问”等 | 进入每日微观问答 |
| 计划日 `DAILY_INTERVIEW_QA` | 用户回答当前题目 | 评价、给标准答案，再给当天下一题 |
| 计划日 `DAILY_DOCUMENTING` | 当天题目已答完 | 写入 `问答.md`，更新当天状态并创建每日 Git commit；提交成功后当天才算 `DONE` |
| 阶段 `WAITING_USER_CODE` | 用户说已写完 | Review 用户代码 |
| 阶段 `REVIEWING` | 用户提交修订 | 重新 Review |
| 阶段 `STAGE_INTERVIEW_QA` | 用户回答当前题目 | 评价、给标准答案，再给下一道宏观题 |
| 阶段 `STAGE_DOCUMENTING` | 宏观题已答完 | 写入 `问答.md`，关闭阶段 |

不要把普通的“好的”“继续”误判为首次编码授权。只有阶段讲解已经完成，且话语明确表达理解并允许实现时，才能从 `EXPLAINING` 进入 `AI_IMPLEMENTING`。阶段授权生效后，仍然一次只执行一个计划日。

## 执行阶段状态机

### 1. 确认需求

先将阶段看板更新为 `REQUIREMENTS_CONFIRMING`，再向用户给出一张简短确认卡：

- 本阶段解决什么用户问题；
- `IN`：本阶段必须交付的能力；
- `OUT`：本阶段明确不做的能力；
- 验收标准与可演示结果；
- 需要用户决定的最多三个关键问题。

只询问会实质改变数据模型、交互或范围的问题。没有未决项时，给出建议默认值并请用户确认。此时只允许只读检查和文档规划，不编写产品代码。

### 2. 讲解设计

用户确认需求后，将阶段看板更新为 `EXPLAINING`。根据用户前端熟悉、后端与数据库等领域较弱的背景，讲清：

1. 用户操作到最终结果的完整数据流；
2. 核心模块的职责和依赖方向；
3. 关键类型、状态、不变量及失败恢复；
4. 技术选择、被放弃的方案及原因；
5. 本阶段测试策略；
6. 计划留给用户的手写点及其面试价值。

Vue 3 基础可以简洁；后端架构、数据库、测试、性能和 Agent 需要用项目内的具体例子解释。必要时使用一个最小流程图或伪代码，避免堆术语。

讲解结束后停在这一关，明确请用户在理解后说“明白了/开始吧”。不要提前创建实现文件或偷偷完成手写点。

### 3. 执行一个计划日

收到阶段授权后，将阶段看板更新为 `AI_IMPLEMENTING`。用户开始或继续某个计划日时，将当天状态更新为 `WORKING`，只完成当天表格中的工作和检查点：

- 由 AI 完成当天绝大部分实现、测试、迁移和必要文档；
- 严守 P0 和当前确认范围，新想法默认进入 backlog；
- 在编码前先检查工作树，保留用户已有改动；
- 优先实现纵向闭环，再补抽象和界面装饰；
- 为关键决策补充简短 ADR，记录“为什么、替代方案、代价”；
- 运行与风险相称的 lint、类型检查、单元、集成或 E2E；
- 不伪造性能、可靠性、Agent 效果或用户数据；
- 到达当天检查点后运行相应验证，不提前执行下一日期的工作。

到达计划中的手写交付日时，只为用户手写点提供：

- 明确的文件与函数签名；
- 输入、输出和不变量；
- 3 至 6 个验收用例；
- 运行测试的命令；
- 不暴露完整答案的分层提示。

保留清晰的 `TODO(user)` 或等价缺口。不得先生成完整实现再让用户照抄。

若当天只是交付手写任务而 Review 安排在下一计划日，先汇报接口、用例和运行方式，再按当天其他已完成工作进行改动导读、理解确认与每日问答。到达手写与 Review 日时，将阶段状态更新为 `WAITING_USER_CODE`。

当天检查点和验证完成后，先将当天状态更新为 `DAILY_WALKTHROUGH` 并执行改动导读，不得直接进入每日微观问答。

### 4. 执行每日改动导读与理解确认

按用户可实际读代码的顺序介绍当天交付，至少包含：

1. 今天解决了什么问题，以及运行后能观察到什么；
2. 新增、修改、删除的文件，按 Web、API、Worker、共享包、基础设施、测试和文档分组说明职责；
3. 从入口到结果的调用链、数据流或依赖方向，并指向具体文件和关键符号；
4. 关键实现、技术取舍、失败路径和当天暂未实现的边界；
5. 建议的代码阅读顺序、启动命令和用户可亲自验证的现象。

不要只列文件名或复述 Git diff；根据用户对后端、数据库、测试、性能和 Agent 不熟悉的背景，先解释目录与进程角色，再解释代码细节。控制首轮导读的信息密度，复杂内容分层展开。

导读结束后停在 `DAILY_WALKTHROUGH`，明确邀请用户查看代码和提问。用户提问时继续结合真实代码回答；若因此修改当天实现，重新运行受影响的验证，并补充讲解新增改动。只有用户明确表示“今天的改动明白了”“可以进入面试题”等理解确认后，才更新为 `DAILY_INTERVIEW_QA`。

普通的“继续”不能代替理解确认。未获得确认时不得展示、暗示或预先写入当天面试题及标准答案。

### 5. 执行每日微观问答

当天检查点、验证和改动导读均完成，且用户已经明确确认理解后，才能将当天状态更新为 `DAILY_INTERVIEW_QA`。为当天准备：

- 默认 1 道题；
- 当天包含两个相互独立且都有高面试价值的知识点时最多 2 道；
- 题目必须绑定当天实际代码、数据流、测试或决策；
- 题目难度为大厂前端日常实习，优先问“为什么、怎样失败、如何验证”，避免只背定义。

一次只展示一道题。用户回答后：

1. 给出明确评价和建议分数；
2. 指出答对的关键点；
3. 指出遗漏、误区与可能被追问处；
4. 给出可在面试中表达的标准答案；
5. 若当天还有题目，只在回复末尾给下一道。

当天最后一题评价完成后，将当天状态更新为 `DAILY_DOCUMENTING`，立即把日期、当日交付、题目、用户回答要点、评价、易错点、标准答案和复习动作追加到 `问答.md`。接着执行每日提交收尾；在准备提交时把当天状态更新为 `DONE`，但只有 commit 成功后才对外确认完成和预告下一计划日。

将状态改为 `DONE` 与每日成果放入同一个 Git commit，并按以下顺序收尾：

1. 执行 `git status --short`，区分当前计划日改动、用户已有改动和无关改动；
2. 只按明确路径暂存当前计划日的代码、测试、必要文档、`问答.md` 与逐日计划状态，不盲目使用会夹带全部工作树内容的暂存方式；
3. 检查暂存差异和 `git diff --cached --check`，确认没有密钥、环境文件、调试产物或范围外内容；
4. 使用能够识别阶段、计划日和核心交付的提交信息创建本地 commit；
5. 再次检查工作树并向用户报告提交哈希、提交主题，以及仍未提交的已有改动。

只有 commit 成功后，才汇报当天为 `DONE` 并预告下一计划日。若提交因 Git 身份、Hook、验证或范围冲突失败，将逐日计划中的当天状态保持或恢复为 `DAILY_DOCUMENTING`，保留安全的工作树内容，说明原因并解决；不得跳过提交关卡。未经用户明确要求，不 amend、rebase、force push 或改写历史。仓库尚无可区分的历史基线时，先说明首个提交必须包含的基线范围，不伪造过去日期的提交。

若当天工作未达到检查点，即使跨过自然日也保持 `WORKING`；不得为了按时提问而把未完成的计划日标记为完成。

### 6. Review 用户代码

用户完成手写后，将阶段看板更新为 `REVIEWING`。检查：

- 正确性和业务不变量；
- 边界、重复事件、并发或失败路径；
- TypeScript 类型设计；
- 时间与空间复杂度；
- 可读性、命名和可测试性；
- 用户能否在面试中解释这段实现。

将问题分为 `blocking` 与 `non-blocking`。存在 blocking 问题时，先解释原因并给针对性提示，让用户修改核心问题；除非用户明确要求，不直接覆盖其实现。仅有机械性小问题时可以代为修整，但必须说明。

Review 通过后运行相关测试，先执行当天改动导读并等待用户理解确认，再进行每日微观问答。手写点每阶段保留 1 个，只有确有独立价值时才增加到 2 个；合计目标耗时不超过 30 分钟。

### 7. 执行阶段宏观问答

只有本阶段所有计划日均为 `DONE` 且用户手写 Review 通过后，才将阶段状态更新为 `STAGE_INTERVIEW_QA`。准备 2 至 4 道大厂前端日常实习难度的宏观问题，满足：

- 必须跨越本阶段两个或更多模块，不能只是重复每日题；
- 至少覆盖一次端到端数据流、技术取舍、故障恢复或架构边界；
- 优先覆盖用户不熟悉的后端、数据库、测试、性能或 Agent，同时保留前端主场；
- 能自然产生面试官追问。

仍然一次只展示一道题，并沿用每日问答的评价格式。每日题不能抵扣这 2 至 4 道宏观题，也不要在用户作答前泄露后续题目或答案。最后一题评价完后进入 `STAGE_DOCUMENTING`。

### 8. 沉淀并关闭阶段

宏观问答全部结束后，将阶段宏观记录追加到根目录 `问答.md`，至少记录：

- 阶段与完成日期；
- 每道题；
- 用户回答的核心观点；
- 评价与分数；
- 从回答识别出的易错点；
- 标准答案；
- 面试前需要复习的行动项。

随后：

1. 将逐日计划中的阶段状态改为 `DONE`；
2. 记录实际完成日期、排期偏差和被裁剪项；
3. 确认代码、测试、文档、所有每日改动导读与理解确认、每日问答、手写 Review 和宏观问答均已完成；
4. 按每日提交的范围检查规则，为阶段宏观问答、阶段状态和排期复盘创建独立的阶段收尾 commit，并报告提交哈希；
5. 只预告下一阶段，不自动开始下一阶段的需求确认。

## 处理排期偏差

将日期视为倒排目标，将流程关卡视为硬约束。用户响应导致日期滑动时，不跳过阶段讲解、每日改动导读与理解确认、每日问答、手写 Review 或阶段宏观问答，也不增加用户手写量来追赶。

按以下顺序恢复排期：

1. 删除 P1、视觉装饰和非关键页面；
2. 使用 PRD 的裁剪顺序减少 P0 外围体验；
3. 将低风险文档和包装工作移到缓冲日；
4. 保持每日题默认 1 道，不通过取消问答追赶；
5. 明确更新逐日计划的实际日期。

若核心链路落后两天以上，立即做范围复盘；若发现会使简历表述失真的缺陷，优先修复而不是按原日期宣布完成。
